# Sisyphus 工作流审计设计

## 任务类型

`non-code`：只读梳理仓库现状、人工审核点和优化空间，不修改实现代码。

## 目标与范围

- 从 Intake 到 Finish 梳理六阶段的输入、职责、产物、责任角色和流转条件。
- 明确区分用户审核、Agent 审核、自动验证与当前缺失的审核。
- 基于仓库证据识别流程漂移、重复工作、不可强制的 Prompt 门禁、并发与恢复风险。
- 给出按优先级排序的提效建议，并说明收益、代价和风险。

## 非目标与约束

- 不修改代码、配置或现有文档。
- 不执行真实 Sisyphus 任务，不把静态 Prompt 契约当作运行时行为证明。
- 不评估或改造 CBM 底层索引器、缓存、watcher 或 daemon。
- 不将 Momus/Oracle 代理审查等同于人工审核。

## 交付结构

1. 六阶段端到端流程表。
2. 人工审核矩阵及自动/Agent 审核边界。
3. 当前实现与文档证据、流程漂移清单。
4. 优化建议：高优先级、中优先级，包含目标、收益、代价/风险。
5. 结论、验证证据和剩余不确定性。

## Metis 分析

### 需求缺口

- 未定义最终是否必须由用户做发布/验收批准。
- 未定义复杂任务的可执行判定阈值。
- Review “每阶段之后”缺少触发、责任人和证据格式。

### 风险

- 主要门禁由 Prompt 驱动，运行时不能强制阻拦越阶段。
- 共享 Worktree 的文件冲突和依赖主要靠模型与 ledger 自觉维护。
- CBM 刷新可能带来最高约 10 分钟的延迟，且降级证据可能不完整。
- Finish 没有独立 Skill，最终验证容易遗漏。

### 边界与非目标

- 纯文档请求不触发 CBM；代码/混合任务才需要索引。
- CBM 失败、超时或 in-progress 时必须 fail-open，但记录降级事实。
- 用户拒绝设计、Momus REJECT、验收证据缺失时不得继续或宣称完成。

### 反例与边界条件

- Metis Intake 后不得无理由重复调用；若需要候选方案分析，应明确使用 `SOLUTION_ANALYSIS`。
- 需求变更应回到分析/计划并重新过门禁。
- 并行任务若 Files、共享状态或依赖冲突，必须串行。
- Agent 完成但无真实表面证据时，任务不能标记 completed。

### 验收标准

- 覆盖六阶段、输入输出、责任 Agent 和审核类型。
- 明确当前唯一强制用户审核为 Brainstorm 设计批准，以及 Plan 的 TDD/Worktree 策略确认；指出缺少强制最终人工验收。
- 覆盖 Prompt/Skill、注册注入、CBM、ledger、运行时观察入口。
- 每项优化包含收益与代价/风险，并引用文件路径和行号证据。

## 方法选择

采用审计型：先以源码、Skill、README 和审查文档交叉核对现状，再输出优化路线；不直接设计实现改造，以避免在事实未统一前扩大范围。
